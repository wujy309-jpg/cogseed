# KSTAR 检索、复用、归因与错误模式优化分析报告

- 日期：2026-09-01
- 分析对象：CogSeed 当前 KSTAR / Recall / Personal Ontology / Group Chat 实现，以及 P3394 Review 文档、KSTAR 优化想法和 9 月 1 日会议记录
- 代码基线：`codex/kstar-develop-rebased-20260901`（核对时 HEAD：`bcc47e69`，对应 `origin/develop`：`71453450`）
- 文档性质：方案分析与实施建议，不等同于已完成实现、联调通过或发版验收

---

## 1. 简单说明

这份报告集中回答五个问题：

1. KSTAR 当前怎样理解任务、检索资产、注入上下文、预测、执行、复盘和沉淀；
2. 为什么会出现“资产已经注入，但模型不一定使用”的问题；
3. 是否需要单独建设一套重型 Error Pattern / Harness；
4. 本体、语义检索、世界模型、跨 Agent 资产分发应该怎样协作；
5. 如何把错误归因转化为高质量、可验证、可复用的经验与规则。

核心结论是：**当前最优先的不是再增加一种“错误模式资产”，而是先补齐资产从检索到生效的真实性证据，升级混合检索与归因质量，并把成熟、高风险的规则编译成确定性门禁。**

## 3. 以上讨论重新整理后的完整问题链

用户提出的观点可以整理为一条连续链路：

```text
任务进入
→ 先做轻量理解，判断需要哪些本体区域
→ 借助本体进一步理解任务
→ 结合本体关联和语义相似度检索其他资产
→ 对候选资产做权限、成熟度、适用性和冲突过滤
→ 注入最小必要资产集
→ 世界模型预测行动、风险和预期结果
→ Runtime / Agent 执行
→ 证明资产是否真正被使用、是否带来效果
→ 对失败进行事实化记录和根因归因
→ 形成可复用经验
→ 归入个人、规则、模板、技能方法四类资产
→ 进入候选池，经验证后晋升和复用
→ 用下一次执行效果验证闭环
```

这条思路总体方向正确，但有四个关键修正：

1. 不是“检索到多少就全部注入多少”，而是只注入**最小、相关、允许、无冲突**的资产集合；
2. 不是“注入的资产必须全部使用”，而是不同资产需要不同约束强度；
3. 本体不能单独承担任务理解和检索，必须与语义检索、当前任务事实共同工作；
4. 错误事实、错误归因、可复用经验和正式规则是四个不同层次，不能在一次模型输出中直接合并为正式资产。

## 4. 当前实现的真实能力与主要缺口

### 4.1 当前已经存在的主链路

当前代码已经具备 KSTAR 主体对象和基本闭环：

```text
Task / Requirement
→ Recall Projection
→ World Model Forecast
→ Runtime / Group Chat / 外接执行
→ Episode
→ Review
→ Extraction / Candidate
→ Ability Asset
```

当前主要相关位置：

- `src/main/features/kstar/`：任务、需求、Episode、Review、Closure、沉淀等；
- `src/main/features/recall/context-projection.ts`：候选资产检索和上下文投影；
- `src/main/features/recall/ontology-taxonomy.ts`：本体分类信息；
- `src/main/features/recall/ontology-rules.ts`：本体规则；
- `src/main/features/recall/projection-knowledge.ts`：Projection 知识组装；
- `src/main/features/recall/rule-engine.ts`：确定性规则判断；
- `src/main/features/recall/world-model-types.ts`：资产、因果规则和世界模型类型；
- `src/main/features/recall/usage-service.ts`：当前 Usage 记录；
- `src/main/features/recall/injection-receipt.ts`：注入收据；
- `src/main/features/group_chat/bus.ts`：Commander 路由、资产分发和执行总线。

### 4.2 当前检索仍主要依赖任务文本的语义匹配

当前实现会把本体分组标题等信息并入资产匹配文本，但 Personal Ontology、T-Box、R-Box 更多是在 Projection 形成后参与世界模型上下文。换句话说，目前更接近：

> **本体信息增强的语义检索**，而不是严格的“先本体定位，再联合检索”。

这会带来三个问题：

1. 任务措辞与资产措辞差异较大时，正确资产可能被漏召回；
2. 语义相近但适用边界不同的资产容易被误召回；
3. 无法充分利用本体中的关系、角色、对象、约束和上下位结构进行候选扩展或收缩。

### 4.3 当前只能证明“注入过”，不能充分证明“使用过”

当前 `recordRecallUsage` 的典型结果仍是：

```ts
outcome: 'injected'
```

跨 Agent 派发时也主要记录：

```ts
outcome: 'dispatched'
```

这些记录证明的是资产进入了提示词或被传递给目标 Agent，却不能证明：

- 模型是否阅读并采纳了该资产；
- 资产是否改变了计划、工具调用或输出；
- 资产是否与任务真正相关；
- 最终效果是否因该资产而改善；
- 资产是否反而造成负迁移。

这就是“已经注入，但不一定使用”的真实根因之一：**系统缺少从 Injection 到 Applied 再到 Effective 的可验证事实层。**

### 4.4 当前归因分类过粗

当前 Review 的归因大致包括：

```text
knowledge_gap
rule_gap
template_gap
skill_gap
execution_gap
unclear
```

它们适合做一级运营统计，但不足以指导自动沉淀。例如同样是 `rule_gap`，实际可能是：

- 根本没有检索到规则；
- 检索到了但 Projection 丢弃；
- 已注入但模型没使用；
- 使用了但规则已经过时；
- 规则之间发生冲突；
- 当前任务根本不适用该规则；
- 工具权限阻止了正确行动。

如果不区分这些原因，沉淀系统会不断生成重复、错误或不可执行的 lesson。

### 4.5 KSTAR Trace 仍缺少关键真实性阶段

当前链路可以表达 routing、task、requirement、projection、forecast、runtime、episode、review、extraction、precipitation、failure 等阶段，但要满足可审计闭环，还需要明确加入：

```text
injection
usage
closure
candidate
trace_completeness
```

并且必须区分：

- 已成功；
- 已失败；
- 被跳过；
- 降级继续；
- 没有发生；
- 没有记录；
- 当前无法判断。

否则 Dashboard 即使显示得很完整，也可能只是“界面完整”，并不代表事实完整。

## 5. 对“错误模式 / Error Pattern Harness”的独立判断

### 5.1 不建议现在建设一套普遍、重型的独立错误模式系统

如果设计成下面这种形式：

```text
每次工具调用前
→ 对错误模式库做向量检索
→ 再调用模型判断是否命中
→ 动态修改提示词或阻断执行
```

其投入和收益通常不成正比，主要原因是：

1. 每一步增加检索延迟、模型延迟和 token 成本；
2. 相似错误不一定具有相同根因，误报会阻断正常执行；
3. 错误描述容易高度重复，候选池会快速膨胀；
4. 它与现有 RuleAsset、CausalRule、Lesson、Review、Candidate 职责重叠；
5. 在 Usage 证据尚未补齐前，无法判断规则是“没注入”“没使用”还是“使用无效”；
6. 系统可能为了避免历史错误而过度保守，降低探索和任务完成率。

### 5.2 更合适的替代方案

不新增第五类 `ErrorPatternAsset`，而是把错误按语义路由到现有四类资产：

| 错误沉淀内容 | 目标资产 |
|---|---|
| 稳定的用户偏好、禁区、个人边界 | `personal` |
| 禁止事项、判断原则、常见陷阱、因果规则 | `rule` |
| 输出格式、字段结构、固定交付形态 | `template` |
| 可重复执行的流程、步骤和工具组合 | `skill_method` |
| 一次性错误、证据不足、不可复用事件 | 只保留 Episode / Review，不生成资产 |

现有 Rule 能力已经可以承载较丰富的错误经验，包括：

```text
statement
applicableWhen
forbiddenWhen
causalRule
ontologyRefs
evidenceRefs
learningSignal
version / maturity / lifecycle
```

其中 CausalRule 至少可以表达：

```yaml
cause: 触发原因
effect: 可能后果
mitigation: 避免或修复方式
severity: 风险等级
deltaR: 对结果的影响
predicateKey: 可选的确定性判断键
```

### 5.3 Harness 应该只用于成熟、高风险、可确定判断的规则

建议将规则分为三层：

1. **普通经验层**：作为推荐上下文注入，不阻断；
2. **强规则层**：必须应用或明确说明不适用；
3. **确定性策略层**：只有经过多次验证、风险高且可由 Host 判断的规则，才编译到工具门禁。

确定性策略启用前应先运行 Shadow Mode：只记录“如果启用将会阻断什么”，不实际阻断。待误报率、漏报率和收益达到标准后，再逐步启用。

## 6. 本体与语义理解：如何避免“鸡生蛋、蛋生鸡”

### 6.1 不能依赖完整本体后才理解任务

任务刚进入时，系统已经拥有最小事实：

- 用户原始指令；
- 当前对话上下文；
- 当前工作区、角色和权限；
- 当前时间和运行状态；
- 显式附件及用户指定对象。

先用这些事实形成轻量 `TaskContract`，并不需要完整理解任务。例如：

```yaml
goal: 用户要完成什么
objects: 涉及哪些对象
action_type: 分析 / 生成 / 修改 / 执行 / 验证
constraints: 显式约束
risk_level: 初步风险
required_capabilities: 初步能力需求
unknowns: 尚不明确的信息
```

然后再用这个轻量契约映射本体锚点，加载最小本体切片，并二次增强理解。它是一个**有边界的两阶段理解过程**，不是无限循环。

### 6.2 推荐的混合检索流程

```text
原始任务与当前运行事实
→ 轻量 TaskContract
→ 映射 Personal Ontology 锚点
→ 加载最小本体切片
→ 生成两路候选：本体关联候选 + 语义相似候选
→ 合并、去重
→ 权限 / 生命周期 / 成熟度 / 适用性 / 冲突门禁
→ 重排
→ 形成最小 ContextProjection
```

其中：

- 本体负责结构、关系、边界、上下位和约束；
- Embedding / 语义模型负责模糊表达、新概念和跨措辞召回；
- 确定性规则负责权限、生命周期、禁止条件和高风险边界；
- 当前用户明确指令永远高于历史偏好，本体不能覆盖本轮显式要求。

## 7. 修复“注入了但没使用”的完整方案

### 7.1 建立五层事实模型

资产流转必须分开记录：

```text
Selected  已被检索选中
Eligible  已通过权限、成熟度、适用性和冲突检查
Injected  已进入目标模型或 Agent 上下文
Applied   已在计划、行动、工具调用或产物中被实际采用
Effective 采用后对结果产生了可观察的正向、负向或中性影响
```

当前 `injected`、`dispatched` 不能继续被当作真实 Usage。

### 7.2 为注入资产增加绑定强度

不是所有资产都要求强制使用。建议增加：

```text
required     必须应用；若不适用，必须给出原因
recommended 建议使用；可忽略，但应留下简短原因
context      仅作背景，不要求逐项声明
```

这样既能修复“关键规则被忽略”，又不会迫使模型机械引用所有背景资料。

### 7.3 Usage 状态不能只靠模型自报

推荐状态：

```text
applied
considered_not_applicable
available_no_opportunity
contradicted
usage_unknown
```

模型可以输出 `claimed_used`，但 Host 必须验证：

1. 该资产确实属于本次已注入集合；
2. 引用的规则、步骤或模板与实际 Action / Tool Call / Artifact 有对应关系；
3. required 资产未使用时是否留下可核验理由；
4. 结果评价能否支持“有效”或“无效”的判断。

### 7.4 推荐的收据结构

```yaml
asset_id: rule-xxx
projection_id: proj-xxx
binding: required
selected_at: ...
eligible_at: ...
injected_at: ...
usage_status: applied
claimed_evidence:
  - action: act-003
host_evidence:
  - tool_call: tc-008
  - artifact: artifact-002
effect:
  status: positive | neutral | negative | unknown
  delta_r: 0.18
reason: 简短解释
```

## 8. 世界模型在链路中的正确位置

推荐顺序是：

```text
TaskContract
→ 最小本体切片
→ 检索其余资产
→ 门禁、最小化并冻结 Projection
→ 世界模型预测 A_hat / R_hat / 风险
→ Runtime 执行
```

世界模型的输入不应是“所有检索结果”，而应是已经通过治理的最小 Projection。Forecast 应保持建议性、非阻断：

- Forecast 成功：为执行提供计划、风险和预期结果；
- Forecast 失败：记录 `no_forecast_baseline` 或等价降级状态，Runtime 继续执行；
- Forecast 错误：Review 需要能够把问题归因为 `forecast_error`，避免错误污染资产沉淀。

## 9. 跨 Agent 资产调用方案

当前由 Commander 统一协调资产分发的方向是合理的：Commander 获得自动 Recall，目标 Agent 不自动拿到全量资产，Commander 显式传递 `ability_assets`，Host 再做验证和结构化注入。

但 Commander 只是**协调者**，不能成为授权主体。目标流程应为：

```text
Confirmed Projection
→ Commander 选择子集
→ Host 验证该子集属于已确认 Projection
→ 与目标 Agent 的角色、能力和权限做交集
→ 结构化注入目标 Agent
→ 记录 Dispatch / Injection / Usage / Effect 收据
```

当前需要重点补的缺口是：除了验证资产存在和运行时可用，还要明确验证资产 ID 是否属于本次已经确认的 Projection，防止 Commander 扩大资产范围或绕过治理边界。

## 10. 归因：决定沉淀质量的核心环节

### 10.1 四个概念必须分开

```text
错误事实：发生了什么
归因：为什么发生
可复用经验：下次应该改变什么
规则资产：经过确认、版本化和验证的持久规则
```

错误事实不能直接变成规则；模型推断的原因也不能直接覆盖确定性证据。

### 10.2 归因输入

归因至少需要：

- Episode：任务、状态、行动、结果；
- Evidence：工具调用、产物、验证结果、错误码；
- Projection：哪些资产被选中和确认；
- InjectionReceipt：哪些资产真正进入上下文；
- UsageReceipt：哪些资产被应用或未应用；
- Forecast：执行前预期，但必须标记其可靠性；
- 当前用户目标是否在执行中发生变化。

### 10.3 推荐的细分归因分类

```text
task_interpretation_error
recall_miss
projection_omission
injection_failure
asset_not_applied
asset_not_applicable
asset_conflict
asset_outdated
execution_error
environment_failure
forecast_error
permission_blocked
user_goal_changed
insufficient_evidence
```

这些可以保留为二级分类，一级仍可汇总到 knowledge/rule/template/skill/execution 等运营口径。

### 10.4 推荐的归因结果结构

```yaml
expected: 预期结果
actual: 实际结果
asset_flow:
  selected: []
  eligible: []
  injected: []
  applied: []
  unknown: []
delta_a: ...
delta_r: ...
error_facts:
  - fact: ...
    evidence_refs: []
root_causes:
  - category: asset_not_applied
    confidence: 0.82
    evidence_refs: []
contributing_factors: []
reusable_experience:
  cause: ...
  effect: ...
  mitigation: ...
  applicable_when: ...
  not_applicable_when: ...
route:
  destination: rule
  action: create_candidate | merge_candidate | update_asset | source_only
  target_asset_id: null
limitations: []
recommended_action: ...
```

### 10.5 归因质量门禁

1. 确定性 Delta 优先，模型只负责语义解释；
2. 模型不能覆盖已记录的事实和错误码；
3. 每个根因必须关联证据并给出置信度；
4. 证据不足时输出 `insufficient_evidence`，而不是编造 lesson；
5. 模型不能直接写正式资产，只能形成候选或更新建议；
6. 必须区分根因与伴随因素，避免把症状沉淀为规则；
7. 用户目标变化、环境故障和权限阻断通常不应沉淀成通用能力规则。

## 11. 从错误到四类资产的沉淀闭环

### 11.1 推荐流程

```text
错误事实
→ 证据绑定
→ 根因归因
→ 提炼可复用经验
→ 判断是否有复用价值
→ 路由到四类资产之一
→ 与已有候选和正式资产查重
→ 新建、合并、更新或仅保留来源
→ 候选池验证
→ 人工或策略确认
→ 晋升正式资产
→ 后续任务验证 Applied / Effective
```

### 11.2 避免重复沉淀

不要同时把 `reason`、`lesson`、`error_pattern` 各生成一份内容相近的资产。建议统一为一个因果经验核心：

```text
Cause → Effect → Mitigation → Applicable Boundary → Evidence
```

重复错误出现时，应优先：

- 给已有候选增加证据；
- 提高或降低置信度；
- 补充适用和不适用边界；
- 更新版本；
- 只有语义和边界真正不同，才创建新候选。

### 11.3 候选晋升条件

建议至少考虑：

- 多次独立证据；
- 归因一致性；
- 正向效果证据；
- 无明显负迁移；
- 适用边界明确；
- 与现有规则无冲突；
- 对高风险规则完成人工确认或确定性验证。

## 12. KSTAR 过程如何做得规范、清晰和可审计

### 12.1 用户视图

用户不需要看到所有内部术语，可以收敛为五个阶段：

```text
理解任务
→ 找到可复用知识
→ 执行并应用
→ 复盘结果
→ 形成新经验
```

每一阶段只显示：状态、简短结论、必要的降级或待确认事项。

### 12.2 技术与审计视图

保留完整 ID、时间、状态和收据：

```text
task_id / requirement_id
projection_id / forecast_id
execution_id / episode_id / review_id
selected / eligible / injection / usage receipts
candidate_id / asset_id
delta_a / delta_r
failure / degraded / skipped / not_recorded
```

设计原则是：**先保证 Trace 真实，再美化 Dashboard。** 如果底层没有 Usage 或 Candidate 事实，界面必须显示“未记录/未知”，不能推断为成功。

## 13. 实施优先级

### P0：真实性契约

1. 分离 Selected / Eligible / Injected / Applied / Effective；
2. 将现有 `injected`、`dispatched` 从 Usage 语义中拆出；
3. 增加真实 UsageReceipt 与证据引用；
4. KSTAR Trace 补齐 injection、usage、closure、candidate 和完整性状态。

### P1：混合检索

1. 增加轻量 TaskContract；
2. 任务映射本体锚点；
3. 加载最小 Personal Ontology 切片；
4. 本体候选与语义候选合并、去重、重排；
5. 加入确定性的权限、成熟度、适用性和冲突门禁。

### P2：跨 Agent 强约束

1. `ability_assets` 必须是已确认 Projection 的子集；
2. 校验目标 Agent 能力、角色和权限；
3. 结构化注入并记录 Dispatch / Injection / Usage；
4. Commander 不得自行扩大权限或资产范围。

### P3：归因升级

1. 扩展二级根因分类；
2. 归因输入加入完整资产流证据；
3. 识别 Forecast 错误、用户目标变化和环境故障；
4. 每条经验必须有证据、边界和置信度；
5. 合并 Episode 级与 Requirement 级重复沉淀路径。

### P4：规则与候选池优化

1. 错误只路由到现有四类资产；
2. 强化 CausalRule 和适用边界；
3. 重复错误优先合并证据，不重复建资产；
4. 用 Applied / Effective 反馈驱动晋升、降级、失效和版本更新。

### P5：高风险确定性门禁

1. 只编译成熟、高风险、可确定判断的规则；
2. 先运行 Shadow Mode；
3. 评估误报、漏报、延迟和任务成功率；
4. 未证明收益前，不上线普遍的逐工具语义 Harness。

## 14. 建议验收指标

### 检索

- Recall Precision；
- Recall Omission Rate；
- 空 Projection 比例；
- 本体锚点命中率；
- 本体候选带来的增量正确召回率；

- Applied → Effective 转化率；
- `usage_unknown` 比例；
- required 规则未遵从率；
- 资产负迁移率；

### 归因与沉淀

- 归因人工纠正率；
- `insufficient_evidence` 合理率；
- 重复候选率；
- 候选合并率；
- 候选晋升后真实复用率；
- 资产更新后效果提升率。

- Recall P95 延迟；
- Forecast P95 延迟；
- Review / Attribution P95 延迟；
- 每任务额外 token；
- Shadow Mode 误报和漏报；
- Trace 完整率和降级可见率。

## 15. 最终结论

1. **关于错误模式**：用户担心 Harness 太重是有依据的。当前不应建设独立、全链路、逐工具的 Error Pattern 系统；应先用现有规则和经验资产承载错误知识。
2. **关于资产检索**：不能继续只依赖语义相似度，也不能改成本体单通道。正确方向是“轻量任务理解 → 最小本体切片 → 本体与语义双路候选 → 确定性门禁 → 最小 Projection”。
3. **关于注入与复用**：问题不只是模型不听提示词，而是系统缺少 Applied 和 Effective 的事实证据。应建立五层资产流和 required/recommended/context 三种绑定强度。
4. **关于归因**：归因确实是沉淀质量的核心瓶颈。必须把错误事实、根因、经验和正式规则分开，并要求证据、置信度和适用边界。
5. **关于沉淀**：错误不需要第五类资产。应按语义归入 personal、rule、template、skill_method；证据不足或不可复用的错误只保留在 Episode / Review。
6. **关于跨 Agent**：Commander 负责协调和选择，但 Host 必须验证资产属于已确认 Projection，并与目标 Agent 权限取交集。
7. **关于 KSTAR 展示**：应先补齐底层 Trace 真相，再做规范和美化；“未记录”和“未知”必须显式展示，不能伪装为成功。

一句话概括：

> **先让 KSTAR 能证明“找到了什么、给了什么、用了什么、为什么有效或无效”，再让它自动从错误中生成更强的规则；否则越自动化，越容易把不可靠归因放大成长期资产。**
