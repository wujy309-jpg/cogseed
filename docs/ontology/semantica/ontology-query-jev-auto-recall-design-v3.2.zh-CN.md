# CogSeed Semantica 自动能力复用设计方案 v3.2

> 状态：历史实验方案，已被 [`ontology-query-local-decision-design-v3.3.zh-CN.md`](./ontology-query-local-decision-design-v3.3.zh-CN.md) 取代。
> 本文保留 Jev 三闸门实验的设计与验收记录，不再作为产品代码、测试或汇报的当前基线。当前产品不要求用户安装、配置或调用 Jev。

## 1. 目标

用户只描述正在做的事情，CogSeed 自动从已经沉淀的能力资产中找到可复用经验，并在需要时沿能力资产之间的本体关系补齐相关经验。

用户不需要知道：

- 能力资产的标题；
- `ontology_query` 工具名；
- `depends_on`、`refines` 等关系类型；
- 本体图谱的实体 ID 或资产 ID。

系统需要做到：

```text
自然任务
  -> 语义检索找到少量入口资产
  -> 以入口资产为起点做受治理的关系扩展
  -> 判断扩展资产是否适用于当前任务
  -> 读取最终选中的资产正文
  -> 将经验用于当前回答
```

这里的 Semantica 是 CogSeed 内部的一条可选增强通道。它不是一个需要用户另外下载的产品，也不是事实数据库；它负责把语义相关性和能力资产关系结合起来。

## 2. 核心边界：Semantica 是可选增强通道

`semanticaEnabled` 是整条自动增强通道的总开关。开关关闭时，不能因为代码已经存在 `ontology_query` 就偷偷执行关系扩展。

用户显式开启 `semanticaEnabled` 后，自动增强通道必须直接生效，不依赖旧的 `COGSEED_RECALL_BASELINE_TOP` 自动正文投影实验变量；该变量只保留用于 Semantica 关闭时的历史基线实验和回滚。

| Semantica | Jev | 自动能力资产行为 |
| --- | --- | --- |
| 关闭 | 任意 | 完全沿用旧的能力资产语义检索；不做自动关系扩展，不调用 Jev，不改变旧排序和回退行为 |
| 开启 | 关闭、未配置或不可用 | 语义入口 + 本地确定性关系扩展 + 本地确定性排序；不调用 Jev |
| 开启 | 开启且可用 | 语义入口 + 本地关系扩展 + Jev 三个判断闸门 + 结果验证 |

### 2.1 关闭时的兼容契约

关闭 Semantica 后，对同一用户问题必须满足：

1. 不执行自动 `ontology_query` 关系遍历。
2. 不执行 `ontology-semantic-orchestrator` 的关系扩展分支。
3. 不发起任何 Jev 网络请求。
4. 继续使用已有能力资产语义检索和治理准入。
5. 返回结果不携带上一次开启 Semantica 时残留的关系候选。
6. 原有普通检索测试、延迟和错误回退不因 Semantica 代码存在而改变。

用户明确要求“查询资产之间关系”也不能绕过总开关。Semantica 关闭时不向模型暴露 `ontology_query`；开启后，现有只读 `ontology_query` 继续作为显式关系查询兼容入口。自动增强和显式关系工具是否可用，都以 `semanticaEnabled` 为唯一总开关。

## 3. 三条运行路径

### 3.1 旧路径：Semantica 关闭

```text
用户问题
  -> 本地硬性治理构建可用资产目录
  -> 旧能力资产语义检索
  -> 读取语义命中的资产正文
  -> 生成回答
```

这条路径是回归基线，不能因为新增功能而被重排或混入关系候选。

### 3.2 增强路径：Semantica 开启、Jev 不可用

```text
用户问题
  -> 本地硬性治理构建可用资产目录
  -> 语义检索选出少量入口资产
  -> 本地确定性关系扩展
  -> 本地适用性和数量限制
  -> 读取最终资产正文
  -> 生成回答
```

这是 Semantica 的最低可用路径。Jev 只是判断增强，不能成为基础能力复用的单点依赖。

### 3.3 完整路径：Semantica 和 Jev 都开启

```text
用户问题
  -> 本地硬性治理构建可用资产目录
  -> 生成有限候选意图
  -> Jev 闸门一：查询前意图判断
  -> 语义检索选入口资产
  -> 本地关系扩展
  -> Jev 闸门二：候选适用性判断
  -> 读取最终资产正文
  -> 生成回答
  -> Jev 闸门三：回答结果观察与验证
  -> 输出回答和可观察回执
```

任何一步 Jev 失败，都回退到同一条不依赖 Jev 的增强路径；任何一步本体扩展失败，都不能编造关系，允许回退到语义检索结果。Jev 的结果判断默认是观察信号，不得单独替换普通任务已经生成的回答或产物。

### 3.4 Jev 结果验证策略

结果验证分为两个策略：

- `observe`（默认）：Jev 仍然判断并写入回执，用于发现证据不足、潜在方向错误和评估误判率；无论 Jev 返回低分、`none`、`clarify` 还是调用失败，都保留已经通过本地硬检查的回答和产物。
- `enforce`（受控实验）：仅允许在明确的本体关系查询实验中显式启用。即使启用，也不能绕过本地硬性检查；该策略不是新任务类型的默认行为。

本地确定性检查仍然是硬边界：越权资产、目录外引用、关系方向反转和直接/间接跳数矛盾可以被本地逻辑拦截。Jev 不能单独成为普通回答的最终否决者。

## 4. 入口资产与关系扩展

### 4.1 为什么必须先选入口

早期单场景测试暴露的问题是：同组演示资产都被语义检索直接命中，最终虽然使用了资产，但无法证明关系遍历发生过。

因此语义检索不能把整个资产池直接作为当前回合记忆。它必须先产生有限的入口候选：

```text
用户问题
  -> semanticTopK(entryAssets)
  -> expandRelations(entryAssets)
```

入口资产不是最终答案，只是关系扩展的起点。

默认建议：

- `entryTopK = 1`，最多可配置为 2；
- 入口候选必须通过目录 v2 和运行时权限治理；
- 入口选择沿用旧语义分数、最低分和作用域规则；
- 入口资产不能因关系扩展被反向补回到已被硬治理拒绝的集合。

### 4.2 默认关系扩展策略

自然任务没有明确关系类型时，使用受限的“相关经验扩展”策略：

- 默认关系：`depends_on`、`refines`、`related_to`、`same_family`；
- 默认方向：`both`，但保留每条边的真实方向；
- 默认最大跳数：2；
- 每个入口最多扩展 8 个候选；
- 全回合关系候选最多 12 个；
- `conflicts_with` 不作为正向经验自动注入，只作为冲突/排除证据；
- `replaces` 只有在用户表达“替代、换成、旧方案不能用”等意图时才扩展。

如果用户明确表达关系意图，则使用查询前意图解析结果覆盖默认策略。例如：

```text
哪些准备依赖工作日双人用餐方案？
```

应生成 `depends_on + incoming` 的有限候选，而不是使用 `both`。

### 4.3 关系与语义可区分的生活示例

演示资产必须能区分“语义直接命中”和“关系扩展命中”。当前使用“工作日用餐”和“周末短途出行”两组共 8 条资产。每组只有入口资产使用用户的日常表达；其他资产分别使用资源、执行和边界管理语言，避免仅靠重复主题词全部被语义检索直接命中。

当语义入口命中“生活演示：工作日双人用餐方案”时，关系扩展应该保留以下证据：

```text
生活演示：库存与采购批次控制
  --depends_on-->
生活演示：工作日双人用餐方案

生活演示：低峰时段批次编排
  --depends_on-->
生活演示：库存与采购批次控制
  --depends_on-->
生活演示：工作日双人用餐方案

生活演示：个体约束隔离
  --refines-->
生活演示：工作日双人用餐方案
```

最终回答可以使用这些经验，但不能把两跳间接关系说成直接关系。

第二组用于排除只对用餐示例特化的实现：

```text
生活演示：交通与费用边界
  --depends_on-->
生活演示：周末短途出行方案

生活演示：低峰窗口选择
  --depends_on-->
生活演示：交通与费用边界
  --depends_on-->
生活演示：周末短途出行方案

生活演示：同行约束隔离
  --refines-->
生活演示：周末短途出行方案
```

关闭 Semantica 时，两组自然任务都只应留下各自的语义入口；开启后，才允许在受治理目录内扩展出对应的直接、两跳和细化关系资产。演示资产只用于工程验收，不替代真实脱敏任务的 A/B/C 收益评估。

## 5. 候选数据契约

关系扩展只传元数据和证据，不在本阶段读取全部资产正文：

```json
{
  "assetId": "aa-example",
  "source": "semantic-entry | ontology-expansion",
  "distance": 0,
  "semanticScore": 0.82,
  "relationKind": "depends_on",
  "evidencePath": [
    {
      "fromTitle": "生活演示：库存与采购批次控制",
      "kind": "depends_on",
      "toTitle": "生活演示：工作日双人用餐方案"
    }
  ],
  "governance": {
    "directoryAdmitted": true,
    "scopeAllowed": true,
    "status": "active",
    "version": "2"
  }
}
```

候选来源必须可区分：

| 来源 | 含义 |
| --- | --- |
| `semantic-entry` | 由当前用户问题直接语义命中的入口 |
| `ontology-expansion` | 从入口沿已持久化关系扩展出来的候选 |
| `semantic_ontology` | 同一资产同时被语义和关系路径支持 |
| `none` | 没有足够证据适用当前任务 |

只有最终选中的资产才进入 `search_ability_assets` 正文读取。不能为了方便把整个受治理目录的正文预先投影给模型，否则关系扩展是否生效仍无法观察。

## 6. Jev 的职责与边界

### 6.1 查询前意图判断

CogSeed 先生成有限候选，Jev 只能判断：

- 在 Semantica 已由用户开启的前提下，沿用默认确定性关系扩展，或选择一个更窄的 `hybrid` 关系计划；
- 关系类型、方向和跳数候选；
- 是否存在需要澄清的歧义；
- 直接关系和间接关系的表达是否一致。

Semantica 总开关决定是否进入增强路径。Jev 返回 `semantic`、`none`、`clarify` 或调用失败时，均不能删除已经由本地治理和确定性关系遍历证明的安全候选；只有选中现有 `hybrid` 候选时，才允许把关系类型、方向或跳数收窄。这样 Jev 是可选的判断层，而不是自动关系复用的单点否决者。

Jev 不能生成新实体 ID、资产 ID、关系边或事实，也不能替代 Semantica 总开关。

### 6.2 查询后候选适用性判断

Jev 只能在已经通过目录 v2、权限、作用域、生命周期和版本校验的候选中选择、排序或返回 `none`。

Jev 不能：

- 恢复被治理过滤的资产；
- 把 `refines` 改判成 `depends_on`；
- 把间接路径改写成直接证据；
- 读取或引用未进入最终候选的正文。

### 6.3 回答后结果验证

验证回答是否被正文和证据路径支持，重点检查：

- 关系方向是否颠倒；
- 直接/间接关系是否准确；
- 是否把“细化”说成“依赖”；
- 是否引入资产正文没有支持的新事实；
- 是否超出当前用户权限和作用域。

验证失败时保守降级、重新生成或明确说明证据不足，不修改资产和本体。

### 6.4 用户回答与内部证据分层

- 普通任务优先输出自然、可执行的答案，不强制展示资产 ID、关系类型、方向、跳数或逐边路径。
- 资产引用、关系路径、Jev 决策和降级状态必须保留在回合级证据包、投影和运行回执中，供校验与审计。
- 用户明确询问来源、资产关系、依据或调试过程时，才按需展示关系和证据细节。
- 缺少用户可见的 `[asset:...]` 标记本身不是拒绝普通任务回答的理由；出现标记时，仍必须检查其是否属于本回合证据集合。
- 这一分层不降低事实约束：关系方向、直接/间接含义和正文支持范围仍在输出前完成校验。

## 7. 治理、隐私和故障边界

执行顺序固定为：

```text
本地硬性治理目录
  -> 语义入口
  -> 本体关系扩展
  -> Jev 判断（如果开启且可用）
  -> 正文读取
```

不得反过来让 Jev 或关系扩展绕过目录治理。

必须满足：

- Semantica 关闭时无 Jev 网络请求；
- Jev 请求不包含目录外、无权限或未最终选中的正文；
- API Key 不进日志、运行回执或 Git；
- 本体图谱为空或关系不存在时明确无覆盖，不编造关系；
- Jev 超时、限流、非法 JSON 或网络错误时回退到本地确定性路径；
- 关系图循环、重复边和超过跳数的候选被丢弃；
- 开关切换不会复用旧回合的关系候选和正文缓存。

## 8. 验证方案

### 8.1 开关对照验收

对同一条自然任务分别执行：

```text
我下周工作日不想点外卖，准备自己在家做晚饭。家里两个人，其中一个人不吃辣，我下班比较晚，每天最多只有半小时做饭。周末可以提前买菜和处理食材，你帮我安排一下这一周应该怎么准备？
```

Semantica 关闭时：

- 保持旧语义检索行为；
- 不出现自动关系扩展候选；
- 不出现 Jev 请求；
- 旧答案和旧回退逻辑不因新功能改变。

Semantica 开启时：

- 先产生一个或少量语义入口；
- 关系候选带有 `ontology-expansion` 来源和证据路径；
- 最终才读取需要使用的资产正文；
- 回答综合计划、采购、备餐和饮食限制经验。

再次关闭后：

- 关系候选消失；
- 不残留上一次回合的资产或证据路径；
- 不发起 Jev 请求。

### 8.2 直接可观察的成功标准

一次自然任务的运行记录至少应能回答：

1. 入口资产是哪一条？
2. 哪些资产是语义命中？
3. 哪些资产是本体扩展？
4. 每条扩展候选的关系类型、方向、跳数和证据路径是什么？
5. 哪些候选被 Jev 采用、拒绝或返回 `none`？
6. 最终正文读取了哪些资产？
7. 是否发生降级？降级到哪条路径？

不能只根据最终回答猜测是否使用了 Semantica。

### 8.3 必测用例

| 用例 | Semantica | Jev | 预期 |
| --- | --- | --- | --- |
| 普通生活任务 | 关 | 任意 | 旧语义检索，零 Jev、零自动关系扩展 |
| 普通生活任务 | 开 | 关 | 入口语义 + 确定性关系扩展 |
| 普通生活任务 | 开 | 开 | 入口语义 + 关系扩展 + 三闸门 |
| Jev 超时 | 开 | 开 | 回退到本地确定性关系扩展 |
| 空本体关系 | 开 | 任意 | 不编造关系，可回退语义检索 |
| 关系方向相反 | 开 | 任意 | 保留真实方向，不错误注入 |
| 间接关系 | 开 | 任意 | 运行记录保留完整路径和跳数；仅在用户明确询问关系或依据时展示 |
| 资产被暂停或无权限 | 开 | 任意 | 不进入扩展候选和正文读取 |
| 切换开关 | 开/关 | 任意 | 结果和工具行为随开关隔离，无缓存污染 |

### 8.4 建议指标

- 入口资产命中率；
- 关系扩展 precision / recall；
- 证据路径完整率；
- 关系方向错误率，目标为 0；
- 直接/间接混淆率，目标为 0；
- 治理绕过次数，目标为 0；
- 资产正文误读率；
- Semantica 开关关闭时的旧链路回归通过率，目标为 100%；
- Jev 降级后增强路径可用率；
- 自动关系扩展带来的回答复用成功率和 P95 延迟。

## 9. 实施顺序

### Phase 7：开关隔离和入口资产模式

- 在 `context-projection` 中读取 `semanticaEnabled`；
- 开关关闭时保留现有语义路径，禁止关系扩展分支；
- 将语义检索结果分成 `entryAssets` 和最终候选，不再默认把所有相似资产作为入口；
- 增加开关对照和缓存隔离测试。

### Phase 8：入口到关系扩展

- 复用现有 `ontology-asset-query` 的受治理遍历能力；
- 从入口资产自动构建有限关系候选；
- 保存来源、跳数和逐边证据路径；
- 只读取最终通过候选门的资产正文；
- 不修改现有显式 `ontology_query` 工具契约。

### Phase 9：Jev 接入增强路径

- 将意图、候选适用性和回答验证接入自动增强路径；
- Semantica 关闭时不触发任何 Jev；
- Jev 不可用时稳定回退本地确定性路径；
- 增加调用次数、超时和降级回执。

### Phase 10：自然任务验收

- 使用生活、工作和项目管理等真实脱敏任务；
- 每条任务同时记录 A（旧语义）、B（Semantica 无 Jev）、C（Semantica + Jev）；
- 验证入口、关系扩展、正文复用和最终答案，不以“工具被调用过”作为唯一标准；
- 达到指标后再决定是否扩大默认灰度。

## 10. 当前结论

当前已经具备：

- 受治理的 `ontology_query` 关系查询链路；
- 能力资产语义检索；
- Jev 适配层和三个判断闸门的独立模块；
