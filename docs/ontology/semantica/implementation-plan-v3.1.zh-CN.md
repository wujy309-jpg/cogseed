## 1. 文档定位

本文档记录本体驱动查询方案 v3.1 的阶段实施历史。当前代码实现、测试和阶段汇报以 v3.3 本地判断方案为准；下文涉及 Jev 的阶段状态只用于解释既有代码和决策演进。

方案目标是：参考 Semantica 的本体驱动思路，在 CogSeed 内部建立一套可复用的查询通道，从用户本体和能力资产中发现、筛选并复用已有能力。当前产品使用本地确定性判断，不依赖外部 Jev 服务。

当前已完成受治理关系查询、语义入口关系扩展和本地回答硬检查。Phase 2 仍是独立规划模块，尚未完成完整的用户本体实体到能力资产自动对齐；仓库内也没有真实脱敏任务集，因此仍不能声称已达到默认开启标准。

## 2. 当前总体链路

```text
用户问题
  -> 规则 / 现有模型生成有限的意图、实体和关系候选
  -> 本地硬性治理构建当前回合可用资产目录
  -> 在已准入目录内执行 ontology_query + search_ability_assets
  -> 本地确定性关系扩展、候选合并和排序
  -> 读取已准入资产正文并生成回答
  -> 本地检查引用集合、关系方向和直接/间接跳数
  -> 输出答案、证据路径和运行回执
```

原 v3.1 的 Jev 三闸门链路已退出产品运行路径，仅在下文保留历史阶段记录。

### 2.1 不可违反的顺序约束

1. 本地硬性治理必须先构建当前回合可用资产目录。
2. 未通过目录治理的资产不能进入本体查询、语义检索、关系扩展或回答证据包。
3. `ontology_query` 负责本体关系查询和证据路径，不负责返回资产正文。
4. `search_ability_assets` 负责读取和检索能力资产正文；长期使用仍通过 `attach_assets_to_task`。
5. 本地判断模块只能处理 CogSeed 已生成的有限候选，不能凭空创建实体、关系、资产 ID 或事实。
6. 判断结果不能直接修改本体、关系、正式资产、权限或目录准入状态。
7. Semantica 关闭时，基础对话和原有能力资产语义检索必须保持原行为。

## 3. 当前基线：Phase 0（已完成）

Phase 0 是后续工作的固定基础，不再重复实现，也不能被后续阶段覆盖。

### 已完成能力

- `ontology_query` 已与 `search_ability_assets` 一起注册到 Recall 工具工厂。
- 查询前复用目录 v2 当前回合快照和统一运行时准入。
- 支持 `depends_on`、`refines`、`replaces`、`conflicts_with`、`related_to`、`same_family`。
- 支持 `incoming`、`outgoing`、`both` 方向。
- 支持有限多跳查询，最多 4 跳。
- 支持资产 ID 和标题定位；标题歧义时返回候选，不静默猜测。
- 返回逐边关系证据路径和治理元数据，不返回资产正文。
- 暂停、过期、无权限、版本不一致或目录外资产不会被关系遍历带出。
- 现有测试覆盖直接关系、多跳关系、方向解析、目标歧义、资产隔离、目录治理和工具注册。

### Phase 0 验收口径

Phase 0 当时的准确口径是：只完成“受治理的能力资产关系查询链路”和独立混合候选编排；后续 Phase 1-6 的增量状态以本文件后续章节和“当前待办状态”为准。完整的用户本体实体到能力资产对齐至今仍未完成。

## 4. 阶段实施计划

### Phase 1：Jev 适配层

**目标：** 建立独立的 Jev 客户端边界，不改变现有 `ontology_query` 行为。

**实施内容：**

- 定义 Jev 请求、响应和判断类型的 TypeScript 类型。
- 支持有限候选判断所需的 `Choice`、`Score`、证据充分性判断等结构。
- 对响应执行严格 schema 校验，拒绝未知问题 ID、非法选项和越界分数。
- 实现 `Noop/Fallback`，无 API Key、关闭开关或 Jev 不可用时直接降级。
- 增加超时、有界重试、错误分类和调用次数限制。
- 对发送给 Jev 的资产摘要进行脱敏，禁止发送未授权正文。
- 增加独立特性开关，默认关闭或保持兼容模式。

**明确不做：**

- 不在本阶段接管自然语言解析。
- 不让 Jev 直接执行本体查询。
- 不让 Jev 修改资产、关系、本体或权限。
- 不改造现有 `ontology_query` 的关系遍历逻辑。

**验收标准：**

- 没有 Jev 配置时现有测试全部通过。
- Jev 超时、网络错误、限流和非法响应都能安全降级。
- 关闭开关后不发起 Jev 请求。
- 请求中不包含目录外或未授权资产。

### Phase 2：查询前意图判断

**目标：** 在执行查询前，把用户问题转换成有限、可验证的结构化意图候选，并由 Jev 选择或拒绝候选。

**候选字段：**

- 查询路由：本体查询、语义检索或需要澄清；
- 目标实体候选及其来源；
- 关系类型；
- 关系方向：`incoming`、`outgoing` 或 `both`；
- 直接关系或间接关系；
- 最大跳数；
- 作用域、版本和其他用户显式约束。

**实施内容：**

- 复用用户本体图谱、T-Box、R-Box 和现有任务契约生成候选。
- 建立用户本体实体到能力资产实体的对齐边界。
- 保留现有自然语言 `ontology_query` 兼容入口。
- 让 Jev 只接受、拒绝、评分候选，或返回需要澄清。
- 实体无法对齐、关系方向不清或候选冲突时，不静默猜测。

**验收标准：**

- 能区分关系方向和直接/间接语义。
- 多个实体或标题有歧义时返回澄清。
- Jev 不可用时沿用确定性解析或回退到语义检索。
- 不允许 Jev 生成未经实体对齐的新资产 ID。
- 不破坏 Phase 0 的所有行为和测试。

**2026-10-02 实施状态：**

- 已新增 `src/main/features/recall/ontology-query-intent.ts`，提供独立的候选生成和 `resolveOntologyQueryIntent` 入口。
- 候选生成复用现有 `parseOntologyAssetQuery`，并可读取用户本体图谱的 active 实体；支持名称、描述和属性的有界确定性匹配。
- 对“直接/间接/多跳”、关系方向、关系类型、目标实体来源和显式约束进行结构化表达；同等实体命中时返回澄清，不静默猜测。
- Jev 只接收本地生成的有限候选；`select`、`score`、`none` 和 `clarify` 均受候选 ID 校验约束。
- Jev 无配置、关闭或调用失败时，使用确定性结果回退；无用户本体图谱时保留资产标题查询兼容路径。
- 已增加 7 个专项测试，覆盖方向、直接/间接、唯一实体、歧义、无图谱兼容、Jev 回退、选择和澄清。

这一步仍是可复用的查询前规划模块，不代表用户本体关系已经能够直接遍历能力资产，也不代表 `ontology_query` 工具已经切换到该规划器。资产目录治理、关系遍历和正文读取仍沿用 Phase 0 链路，统一接入属于 Phase 3。

### Phase 3：本体查询与语义检索统一编排

**目标：** 在同一个受治理目录内合并本体关系召回和能力资产语义召回。

**实施内容：**

- 统一本体候选和语义候选的数据结构。
- 记录候选来源：本体关系、语义检索或两者同时命中。
- 保留关系类型、方向、跳数和逐边证据路径。
- 复用目录 v2 的权限、作用域、敏感度、版本和生命周期治理。
- 建立候选合并、去重和确定性排序规则。
- 为后续 Jev 候选适用性判断提供稳定输入。

**明确不做：**

- 不把语义相关性当成本体事实。
- 不因本体命中而自动读取或采用资产。
- 不把关系命中、正文已读和资产已采用混为一个状态。

**验收标准：**

- 本体和语义两路结果能够稳定合并。
- 目录外资产不会通过语义检索或关系遍历进入结果。
- 候选来源和证据路径可追溯。
- 原有单独使用 `ontology_query` 和 `search_ability_assets` 的行为不变。

**2026-10-02 实施状态：**

- 已新增 `src/main/features/recall/ontology-semantic-orchestrator.ts`，在调用方提供的目录 v2 准入资产集合内统一编排本体候选和语义候选。
- 复用 `mergeHybridMatches` 的双路去重、来源标记、确定性排序、类型多样性和 `limit` 规则；本体查询结果可保留关系类型、方向、跳数和逐边证据路径。
- 目录外候选会在编排边界被丢弃；统一结果只返回资产元数据、分数、来源和本体证据，不读取或携带资产正文。
- 语义检索降级时仍可返回可靠的本体候选，并显式返回降级状态；本体遍历、权限治理和正文读取仍由既有链路负责。
- 已增加专项测试，覆盖双路命中、单路来源隔离、证据路径、目录边界、去重、稳定截断和语义降级。

这一步完成的是可复用的候选编排边界，不代表用户本体实体已经自动对齐能力资产。其输出目前已由 Phase 4 的 Jev 候选适用性闸门消费。

### Phase 4：查询后候选适用性判断

**目标：** 对已经通过本地硬性治理的有限候选进行选择、排序或拒绝。

**实施内容：**

- 将关系候选和语义候选以最小必要摘要发送给 Jev。
- 让 Jev 判断资产是否适合当前任务，而不只是判断图上是否相连。
- 支持选择候选、重新排序或返回 `none`。
- 对低置信度、高敏感度或冲突候选采取保守策略。
- Jev 失败时回退到确定性排序。

**验收标准：**

- 只有本地准入候选才能进入 Jev。
- `none` 不会被改写成任意候选。
- Jev 不能恢复权限过滤、暂停或过期资产。
- 低置信度不会自动注入高风险正文。
- Jev 关闭时仍能使用现有候选排序。

**2026-10-03 实施状态：**

- 已新增 `src/main/features/recall/ontology-candidate-suitability.ts`，只接收 Phase 3 产出的有限统一候选，并已接入 `context-projection.ts` 的现有投影选择流程。
- 发给 Jev 的候选最多 32 条，只包含资产 ID、标题、类型、作用域、成熟度、版本、召回来源、分数和本体证据路径，不包含资产正文或来源正文。
- `select` 只接受本地候选 ID 并按返回顺序选择子集；`score` 按适用性分数重排，默认低于 `0.5` 的候选不进入后续正文读取；`none` 和 `clarify` 均返回空候选，不会用原排序偷偷补回。
- Jev 关闭、缺少配置、超时、限流或响应非法时保留 Phase 3 的确定性排序；关闭或未配置不会发起网络请求，也不会被记录为检索降级。
- 目录 v2 和运行时硬闸仍负责权限、作用域、适用/禁用条件、敏感度、版本和生命周期；Jev 无权恢复硬闸已经过滤的资产。
- 已增加 6 个专项测试，覆盖关闭回退、最小请求、选择和重排、低分过滤、`none`、澄清以及目录外 ID 不可恢复。

这一步完成的是查询后候选适用性闸门。Jev 仍不是事实来源；回答输出由后续 Phase 5 闸门独立验证。

### Phase 5：回答后结果验证

**目标：** 检查最终回答是否被已读取资产正文和关系证据路径支持。

**验证输入：**

- 用户原问题；
- 最终回答；
- 已读取资产的必要正文或摘要；
- 本体关系证据路径；
- 直接/间接关系标记；
- 资产治理和作用域信息。

**重点检查：**

- 关系方向是否正确；
- 是否把间接关系写成直接关系；
- 是否超出资产正文或证据路径；
- 是否遗漏冲突、权限或作用域限制；
- 没有充分证据时是否明确表示证据不足。

**失败处理：**

- 重新生成回答；
- 降级为确定性的证据回答；
- 或明确返回无法确认，不编造事实。

**当前策略修正：**

- 结果验证默认是 `observe` 模式：Jev 的低分、`none`、澄清或服务失败只产生质量信号和回执，不替换普通任务已经生成的回答或文件；
- 本地确定性硬检查继续拦截目录外引用、关系方向反转和直接/间接跳数矛盾；
- `enforce` 仅作为明确的本体关系查询实验策略，必须由调用方显式指定，不能因为新增任务类型而自动启用。

**验收标准：**

- 验证失败不会修改正式资产、本体或关系。
- 验证结果只产生质量信号和运行回执。
- Jev 不可用时系统仍能输出保守、可追溯的回答。
- 普通任务不要求在用户可见回答中打印资产 ID、关系类型、跳数或证据路径；这些信息由内部证据包和运行回执保留，用户明确询问来源或关系时再展示。

**2026-10-03 实施状态：已完成。**

- `ontology_query` 成功返回关系结果，或 `search_ability_assets(assetIds)` 实际读取通过治理准入的正文后，才激活当前回合的最终回答闸门；目录模式、仅语义搜索和普通对话不触发。
- 终局模型文本先暂存在 Core Agent 内部，验证通过或替换为保守证据答案后才写入会话并流给界面；工具调用中间轮仍保持原有流式行为。
- 本地硬检查覆盖证据存在、已出现的可见引用属于本回合证据、关系方向颠倒以及直接/间接跳数冲突；普通任务没有可见引用不再单独构成拒绝原因，成功但零匹配的本体查询仍作为有效负向证据处理。
- Jev 只接收一个有限的回答草稿候选及本回合证据；默认 `observe` 模式下，`none`、澄清或低分只记录复核信号并保留原回答，`enforce` 模式才允许在受控关系查询实验中改为确定性保守答案。
- Jev 关闭或缺配置时不发网络请求；本地硬检查通过则保留原答案，验证器异常不得吞掉已经生成的回答或文件。
- 自然任务的保守答案只呈现可用经验，不默认输出本体箭头、关系名和跳数；技术关系查询仍可按需输出关系结论。
- 运行回执只保存哈希、资产 ID、关系路径数量、状态和降级元数据，不保存原问题、完整回答或资产正文。
- Jev 不能单独否决普通任务的最终回答；新增任务类型默认继承 `observe`，不得因为关键词命中而隐式开启 `enforce`。
- 专项测试覆盖验证器、最终流式闸门和工具触发边界；Phase 1-5 可运行定向集合共 97 项通过。依赖 Electron 原生运行时的资产工具集成入口仍受本机 Electron 安装不完整阻断。

### Phase 6：脱敏数据对照评估与灰度启用

**目标：** 在不提交真实用户数据的前提下，验证本体驱动查询、语义检索和 Jev 闭环的收益与风险。

**测试覆盖：**

- 直接关系和有限多跳关系；
- 正向、反向和双向查询；
- 实体或标题歧义；
- 本体无覆盖时回退语义检索；
- 资产无权限、已暂停、过期或版本不一致；
- 候选为空或 Jev 返回 `none`；
- Jev 超时、限流、非法响应和服务不可用；
- 直接/间接关系表述错误；
- 普通对话和普通检索不依赖 Jev。

**建议灰度顺序：**

```text
Jev 全关闭
  -> 只开启 Phase 2 意图判断
  -> 开启 Phase 4 候选适用性判断
  -> 开启 Phase 5 结果验证
  -> 三个闸门全部开启
```

**评估指标：**

- 本体查询和语义检索的命中率、准确率和回退率；
- 关系方向、跳数和实体对齐正确率；
- Jev 各闸门调用成功率、降级率和增益；
- 误选、漏选、误判直接关系的比例；
- 单任务 Jev 调用次数、延迟和成本；
- 硬性治理绕过次数，目标为 0。

**2026-10-03 工程实施状态：已完成；真实数据结论：待评估。**

- 新增严格的脱敏数据 schema、A/B/C 三路采集接口、指标计算器和命令行入口 `npm run eval:ontology`。
- 指标覆盖 precision、recall、F1、MRR、`none`、意图、证据、方向、跳数、错误注入、治理绕过、降级稳定性、延迟、调用次数和成本。
- 放量判定器默认要求至少 30 个脱敏 case 和全部场景覆盖；任一安全、质量、延迟或成本门槛失败均返回 `not_ready`，且不会自动修改线上配置。
