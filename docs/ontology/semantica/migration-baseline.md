## develop 已有的可复用实现

最新 develop 已经提供了本体和能力资产复用的基础，不需要从旧分支整套覆盖：

- `src/main/features/ontology_graph.ts`：用户本体图谱的分类、实体和关系存储
- `src/main/ipc/ontology-graph.ts`：本体图谱 IPC 边界

这些模块共同构成目前的“本体驱动能力复用基础”。它们读取用户运行时沉淀的数据，不内置 `985/211`、员工或 API 网关等业务事实。

## 2026-10-01 认知资产合流后的首条查询链路

本分支已在 `origin/develop@460911c2` 的认知资产合流基线上完成第一条实际接入：

- 新增 `ontology_query`，与 `search_ability_assets` 一起由现有 Recall 工具工厂注册；
- 查询前复用目录 v2 的当前回合快照和统一运行时准入，不另建资产池；
- 读取正式资产的 `relations`，支持按关系类型、方向和最多四跳导航；
- 目标资产按 ID 或标题解析，歧义时返回候选而不静默猜测；
- 结果只返回治理元数据和逐边证据路径，不返回资产正文；
- 正文仍必须通过 `search_ability_assets(assetIds)` 读取，长期使用仍通过 `attach_assets_to_task` 挂载；
- 查询结果沿用目录观察回执，不把“关系命中”误记为“正文已读”或“资产已采用”。

当前尚未实现：

- 从用户本体图谱实体跨到能力资产的统一实体对齐；
- T-Box/R-Box 规则推演后的资产候选扩展；
- Jev 查询前意图判断的统一主流程接入；
- 本体候选、语义候选和 Jev 判断的脱敏对照评估与默认策略。

这是一条 2026-10-01 的阶段记录：当时只完成“受治理的能力资产关系查询链路”。后续 Jev 与评估增量以本文后续章节为准；完整 Semantica 式用户本体实体对齐至今仍未完成。

Phase 1 完成不代表 Jev 已经参与任何用户查询；Phase 2 已完成独立规划模块，Phase 3 已完成候选编排，Phase 4 已把查询后候选适用性闸门接入投影选择流程。

## 2026-10-02 Phase 2 查询前意图规划

本分支已完成 Phase 2 的独立规划模块：

- `ontology-query-intent.ts` 从自然语言和现有资产关系解析器生成有限结构化候选；
- 有用户本体图谱时，对 active 实体进行名称、描述和属性的确定性对齐；
- 输出路由、目标实体、关系类型/关系词、方向、直接/间接范围、最大跳数和约束；
- 多个同等实体候选返回澄清，不让 Jev 静默创建或选择本地不存在的实体；
- Jev 未配置时使用确定性回退，不发起网络请求；Jev 仅能选择、评分、拒绝或要求澄清已有候选；
- 保留无图谱时的资产标题查询兼容行为。

该模块尚未接入 `ontology_query` 的主工具执行，也未实现用户本体实体到能力资产候选的统一对齐。后续仍需接入查询前主流程，但不能修改已有受治理关系遍历。

## 2026-10-02 Phase 3 统一候选编排

本分支已完成 Phase 3 的独立候选编排边界：

- `ontology-semantic-orchestrator.ts` 接收调用方已经完成目录 v2 准入的资产集合，不自行读取或重建资产池；
- 复用现有 `hybrid-retrieval.ts` 的双路合并、去重、确定性排序、类型多样性和数量限制；
- 输出本体、语义或双路命中来源，并保留本体查询的关系类型、方向、跳数和逐边证据路径；
- 目录外候选不会进入结果，结果不携带资产正文；语义检索降级时可保留本体候选并返回降级标记；
- 已增加专项测试，未修改已有 `ontology_query` 受治理关系遍历逻辑。

Phase 3 本身只建立候选编排边界；其输出目前已由 Phase 4 的候选适用性闸门接入现有投影选择流程。

## 2026-10-03 Phase 4 查询后候选适用性判断

本分支已完成 Phase 4 并接入现有投影选择流程：

- `ontology-candidate-suitability.ts` 将 Phase 3 的有限候选转换为不含正文的 Jev 最小请求；
- Jev 只能选择、评分、返回 `none` 或要求澄清本地候选，不能创建或恢复目录外资产；
- 评分低于默认阈值 `0.5` 的候选不会进入后续正文读取，`none` 和澄清不会被确定性候选覆盖；
- Jev 关闭、缺配置或调用失败时保留原有确定性排序，现有普通检索不依赖 Jev 可用性；
- 目录和运行时硬闸继续负责权限、作用域、适用/禁用条件、敏感度、版本和生命周期；
- 已增加 6 个专项测试，并通过类型检查、ESLint 和 Phase 1-4 定向测试。

Phase 4 当时只完成候选选择，不代表回答已经经过证据验证；该缺口现已由下面的 Phase 5 补齐。

## 2026-10-03 Phase 5 回答后结果验证

本分支已完成 Phase 5 并接入 Core Agent 最终回复边界：

- `ontology_query` 成功或按 ID 实际读取准入资产正文后，收集仅限当前回合的关系与正文证据；目录浏览、仅语义搜索和普通对话不触发验证。
- 终局文本在验证前不会写入会话或流给界面；验证失败、低分、`none` 或异常时替换为确定性的保守证据答案。
- 本地硬检查覆盖证据存在、资产引用越界、关系方向颠倒和直接/间接跳数冲突；零匹配本体结果可作为负向证据。
- Jev 仍只能判断有限的回答草稿候选，不能补造事实、资产或关系；关闭或缺配置时不联网。
- 验证回执只保存哈希、资产 ID、状态、关系路径数量和 Jev 降级信息，不保存原问题、正文或完整回答。
- 类型检查、ESLint 和 Phase 1-5 可运行定向测试通过（97 项）；完整 Electron 测试入口被本机不完整的 Electron 安装阻断。

Phase 5 完成不代表 Jev 服务已经配置，也不代表三路真实数据评估已经完成。下一阶段是 Phase 6 脱敏对照评估与灰度启用。

## 融合原则

- 以最新 develop 的数据模型和治理边界为准，不覆盖其已有实现。
- 先通过本地测试验证，再决定是否提交或推送。
- 不把本地真实资产和本体数据复制进 Git。
- 新增查询入口时，应复用现有用户身份、作用域、资产版本和投影准入逻辑。
- Jev 只能判断 CogSeed 已生成的有限候选：可用于查询前意图判断、查询后候选适用性判断和回答后结果验证，但不能替代实体对齐、本体图谱、关系遍历或 CogSeed 的权限治理。
