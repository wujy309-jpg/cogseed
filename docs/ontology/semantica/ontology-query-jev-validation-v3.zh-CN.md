# CogSeed 本体驱动查询与 Jev 验证方案 v3.1

> 2026-10-06 设计增量：自然任务的语义入口、自动关系扩展、Semantica 总开关兼容契约和自然任务验收，改由 [`ontology-query-jev-auto-recall-design-v3.2.zh-CN.md`](./ontology-query-jev-auto-recall-design-v3.2.zh-CN.md) 定义。本文继续保留 v3.1 的三路验证框架和历史验收记录。

> 目标：验证“CogSeed 自己的本体驱动查询 + 多阶段 Jev 判断层”是否比纯语义检索更可靠，而不是验证某些固定示例数据是否存在。

## 1. 被测方案

在同一批用户沉淀的、脱敏的实体、关系、能力资产和任务上比较三条路径：

```text
A. search_ability_assets
   能力资产纯语义检索

B. ontology + existing ranking
   本体查询 / 关系证据 + 现有确定性排序

C. ontology + Jev
   候选意图 + Jev 意图判断 + 本体查询 / 关系证据
   + Jev 候选适用性判断 + Jev 结果验证 + 现有治理闸门
```

Jev 失败时，C 必须降级到 B；本体没有覆盖时，B 和 C 可以回退到 A。任何路径都不能绕过权限、作用域、敏感度、版本和资产生命周期检查。

### 1.1 Jev 在链路中的位置

Jev 不是独立的自然语言解析器，也不是事实来源。它不负责凭空生成实体、关系、方向和跳数，而是在 CogSeed 已经生成有限候选后，判断候选是否成立。推荐链路如下：

```text
用户问题
  -> 规则 / 现有模型生成候选意图和实体候选
  -> 本地硬性治理构建当前回合可用资产目录
  -> Jev 意图判断闸门
  -> 在已准入目录内执行本体查询 + 能力资产语义检索
  -> Jev 候选适用性判断
  -> 按需读取已准入资产正文并生成回答
  -> Jev 结果验证
  -> 输出答案、证据和回执
```

三个 Jev 闸门职责如下：

| 闸门 | 判断问题 | 可以产生的结果 | 不能做的事 |
| --- | --- | --- | --- |
| 意图判断 | 是否应走本体查询；候选关系、方向和直接/间接含义是否符合原问题 | 接受、拒绝、评分、要求澄清或回退语义检索 | 不凭空抽取实体，不直接执行查询 |
| 候选适用性 | 已准入的关系候选是否真正适用于当前任务 | 选择资产、排序或返回 `none` | 不恢复被治理闸门过滤的资产 |
| 结果验证 | 最终结论是否被资产和关系证据支持 | 通过、拒绝、质量分或要求重新生成 | 不成为新的事实来源，不直接改写正式资产 |

意图判断必须采用“先生成候选、再判断”的方式。例如先生成 `认证服务 depends_on API 网关` 和反向关系两个结构化假设，再由 Jev 判断哪个假设更符合用户原话。目标实体最终仍须通过 CogSeed 的实体对齐确认。

执行顺序约束：本地硬性治理必须先构建当前回合可用资产目录；只有目录内已准入的资产才能参与本体关系查询、语义检索和后续 Jev 候选适用性判断。意图判断可以在目录构建后对有限结构化候选做路由判断，但不能读取、恢复或放行目录之外的资产。

## 2. 测试数据边界

测试数据应来自用户实际沉淀的数据，或者来自明确标注的脱敏夹具。不能把 `985/211`、员工、API 网关等会议例子写进产品默认数据。

每条样本至少包含：

```json
{
  "id": "case-001",
  "task": "用户任务原文",
  "ontology": {
    "entities": [],
    "relations": [],
    "paths": []
  },
  "candidateAssets": [],
  "expected": {
    "route": "ontology-or-semantic",
    "intent": {
      "targetEntityId": null,
      "relationKind": null,
      "direction": null,
      "maxHops": 1,
      "needsClarification": false
    },
    "assetIds": [],
    "allowNone": true,
    "evidenceRelations": []
  },
  "sensitivity": "synthetic-or-redacted"
}
```

标注结果由人工确认，至少包含：正确查询路由、结构化意图、正确候选、明确不应选择的候选、允许返回 `none` 的条件和应展示的证据路径。

## 3. 功能验证

### 3.1 本体查询正确性

验证：

- 实体名称和别名能对齐到用户本体中的实体；
- 关系方向正确；
- 反向关系查询正确；
- 1-2 跳导航不重复、不循环；
- 关系不存在时明确返回无覆盖，而不是编造结果；
- 返回实体、关系、来源和路径证据。

验收建议：

- 关系查询 precision >= 0.90；
- 关系查询 recall >= 0.85；
- 证据路径完整率 >= 0.95；
- 不存在关系时编造率 = 0。

### 3.2 候选资产复用正确性

验证：

- 本体关系能够召回正确能力资产；
- 资产必须先通过本地硬性准入；
- `conflicts_with`、禁止条件和作用域限制生效；
- 已暂停、过期、版本不一致或无权限资产不能进入 Jev 输入；
- 候选为空时可以安全回退。

### 3.3 Jev 结构化判断

验证三个判断时机：

#### 3.3.1 查询前：意图判断闸门

- 输入只包含用户问题、结构化候选意图和必要的实体候选摘要；
- 判断是否应该进入本体关系查询，或者回退到普通语义检索；
- 判断关系类型、方向、直接/间接含义是否与用户原话一致；
- 多个候选均不可靠时返回低置信度或“需要澄清”，不能静默猜测；
- Jev 只能接受、拒绝或评分候选，不能直接生成未经实体对齐的新 ID；
- Jev 不可覆盖用户显式提供的资产 ID、关系类型或作用域约束。

#### 3.3.2 查询后：候选适用性闸门

- 只有通过本地硬性治理准入的候选才能进入 Jev；
- 判断关系上命中的资产是否适用于当前任务，而不只是“图上相连”；
- 支持选择候选、重新排序或返回 `none`；
- 低置信度不得自动读取或注入高风险资产正文。

#### 3.3.3 回答后：结果验证闸门

- 判断回答是否被已读取资产和关系证据路径支持；
- 检查是否把间接关系误写成直接关系、颠倒关系方向或超出证据范围；
- 普通任务的资产 ID、关系名、跳数和逐边路径保留在内部证据与回执中，不要求每次在用户可见回答中展示；用户明确询问来源或关系时再展示；
- 验证失败时重新生成、降级为确定性结果或明确表示证据不足；
- 验证结果只产生质量信号，不直接修改本体、关系或正式资产。

三个时机均可复用 Jev 的结构化问题类型：

- `Choice`：选择候选资产或 `none`；
- `Score`：对适用性、相关性和结果质量评分；
- `Noul`：判断适用条件、证据充分性和冲突陈述。

验收：

- 返回结果通过本地 schema 校验；
- 未知 question ID、非法选项和越界分数被拒绝；
- 低置信度不自动注入高风险资产；
- `none` 不被改写成任意候选；
- 关系方向判断错误或实体歧义时能够澄清或降级；
- Jev 结果不能直接修改本体或正式资产。

## 4. 降级和故障验证

必须覆盖：

| 故障 | 预期行为 |
| --- | --- |
| 没有 Jev API Key | 不调用 Jev，走 B 或 A |
| 意图判断超时或非法 | 使用现有意图解析结果；低置信度时澄清或回退到能力资产语义检索 |
| 候选判断超时或非法 | 记录降级，走 B 的现有排序 |
| 结果验证超时或非法 | 保留有确定性证据的结果并标记未验证，不扩大结论 |
| Jev 限流 | 有界重试，随后降级 |
| Jev 网络错误 | 不影响主对话 |
| 本体图谱损坏或不可读 | 不编造关系，按策略回退 |
| 本体无相关实体 | 明确无覆盖，允许语义检索 |
| 候选全部被权限过滤 | 返回无可用资产，不发送给 Jev |
| 本体和资产版本变化 | 重新计算或拒绝旧结果 |

关键验收：CogSeed 的基础对话和普通检索不依赖 Jev 可用性。

## 5. 安全和隐私验证

检查：

- API Key 不出现在日志、回执和仓库；
- 未授权资产正文不进入 Jev 请求；
- 请求只发送完成判断所需的最小 state；
- 用户关闭 Jev 后不再发起请求；
- Jev 返回文本按不可信数据处理，不作为系统指令执行；
- Jev 不可直接写资产、本体、关系或权限配置；
- 跨作用域和高敏感资产需要本地确认流程；
- 回执记录摘要和引用，不默认记录完整敏感正文。

## 6. 质量和效果指标

对每条任务记录：

```json
{
  "caseId": "case-001",
  "route": "ontology_jev",
  "intentGate": "accepted",
  "intentCorrect": true,
  "selectedAssetIds": [],
  "expectedAssetIds": [],
  "precision": 0,
  "recall": 0,
  "mrr": 0,
  "noneCorrect": false,
  "hardGateViolations": 0,
  "latencyMs": 0,
  "jevLatencyMs": 0,
  "jevCalls": 0,
  "jevStage": ["intent", "candidate", "result"],
  "fallback": false,
  "resultQuality": 0,
  "evidenceComplete": false
}
```

核心指标：

- 候选 precision / recall / F1；
- 本体查询路由准确率；
- 目标实体、关系类型和方向的意图准确率；
- 正反关系颠倒率和不必要澄清率；
- 正确 `none` 比例；
- 资产复用成功率；
- 错误注入率；
- 权限或作用域绕过次数，必须为 0；
- 证据路径完整率；
- 各 Jev 闸门的调用成功率、降级率和增益；
- P50/P95 延迟；
- 单任务 Jev 调用次数；
- 单任务调用成本；
- 用户纠正率和撤销率。

## 7. 对照验收门槛

建议先使用离线评估集，不直接改变默认线上行为。候选默认开启需要同时满足：

1. C 的候选 F1 不低于 B，且明显优于 A；
2. 错误注入率不高于 B；
3. 硬性治理绕过次数为 0；
4. `none` 判断准确率达到人工可接受门槛；
5. Jev 降级后 B 的行为保持稳定；
6. P95 延迟和成本在产品预算内；
7. 不同数据规模、空本体和脏关系数据下没有严重退化。

## 8. 分阶段验收

### Phase 1：适配器验收

只验证 Jev 客户端和 `Noop/Fallback`：请求构造、响应校验、超时、重试、脱敏和降级。

### Phase 2：意图判断验收

验证“候选意图生成 -> Jev 判断 -> 查询路由”：覆盖本体/语义路由、关系类型、方向、跳数、实体歧义、澄清和失败降级。此阶段 Jev 只判断有限候选，不承担自由实体抽取。

### Phase 3：统一候选编排验收

验证本体查询和语义检索是否在同一份目录 v2 准入集合内稳定合并：覆盖双路命中、单路命中、去重、确定性排序、数量限制、目录外候选过滤、关系证据路径保留和语义检索降级。该阶段不调用 Jev，不读取资产正文，也不改变已有 `ontology_query` 遍历。

### Phase 4：候选适用性验收

验证本体证据经过硬闸后进入 Jev，Jev 选择或拒绝候选，失败回退到现有排序。

**2026-10-03 验收状态：通过专项验收。** 已覆盖最小元数据请求、候选选择与重排、低分过滤、`none`、澄清、未知资产 ID 拒绝和 Jev 不可用时确定性回退；目录与运行时硬闸仍在 Jev 之前执行，资产正文不进入该闸门请求。

### Phase 5：执行前与结果验证验收

验证作用域、版本、冲突和敏感度策略不被 Jev 结果绕过；验证最终回答得到证据支持，失败时能够重新生成或保守降级。Jev 只产生质量信号，不绕过现有资产候选、审核和晋升流程。

**2026-10-03 验收状态：通过专项验收。** 已验证正文读取和成功本体查询会激活最终回答闸门，目录、仅语义搜索和普通对话不触发；终局草稿在验证前不流出，工具中间轮保持原流式；本地硬检查覆盖无证据、引用越界、方向颠倒、直接/间接跳数错误和零匹配负向证据；Jev `select`/评分、`none`、低分及未配置降级均有覆盖；回执不包含原问题、完整回答或资产正文。Phase 1-5 可运行定向集合共 97 项通过，完整 Electron 集成入口因本机 Electron 安装不完整未运行。

### Phase 6：真实数据对照验收

在获得脱敏真实任务集后，比较 A、B、C 三条路径，并形成是否默认开启的结论。

**2026-10-03 工程状态：评估与灰度工具链已完成，真实数据验收尚未开始。** 当前已有严格数据 schema、A/B/C 强制采集器、指标报告、`ready/not_ready` 放量判定、命令行入口、按闸门白名单和稳定百分比分桶。由于没有真实脱敏任务集和 Jev API Key，当前不得填写收益结论或默认开启 Jev。数据准备和执行步骤见 `phase6-evaluation-guide.zh-CN.md`。

## 9. 明确不能作为验收的内容

- 只拿固定的 API 网关示例证明通用能力已经完成；
- 只看到 Jev 返回 JSON 就认为资产复用正确；
- 让 Jev 在没有候选意图和实体对齐的情况下自由猜测查询结构；
- 让 Jev 的意图判断覆盖用户显式参数或本地硬性治理；
- 只验证本体图谱能保存数据，就认为自然语言查询已经完成；
- 只验证向量召回数量，不验证关系方向和证据；
- 把 Jev 的判断当作事实来源；
- 把方案文档、测试脚本或演示夹具当成生产闭环。

## 10. 当前基线结论

最新 develop 已有本体图谱、R-Box、任务契约、目录 v2、混合资产检索和资产投影准入测试。迁移分支已完成受目录准入约束的 `ontology_query`、Phase 1-5 代码链路，以及 Phase 6 的评估与灰度工程。用户本体实体到能力资产的统一对齐、查询前意图主流程接入、真实 Jev 配置和真实脱敏三路数据结论尚未完成。

当前只能验收为：

> CogSeed 已具备参考 Semantica 思路的本体驱动能力复用基础，已完成 Phase 1-5 代码链路和 Phase 6 评估/灰度工具链；查询前意图主流程接入、真实 Jev 配置与真实脱敏 A/B/C 收益结论仍未完成，当前默认不开启 Jev。
