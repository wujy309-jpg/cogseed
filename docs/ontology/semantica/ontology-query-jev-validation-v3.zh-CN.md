# CogSeed 本体驱动查询与 Jev 验证方案 v3

> 目标：验证“CogSeed 自己的本体驱动查询 + Jev 判断层”是否比纯语义检索更可靠，而不是验证某些固定示例数据是否存在。

## 1. 被测方案

在同一批用户沉淀的、脱敏的实体、关系、能力资产和任务上比较三条路径：

```text
A. kb_search
   纯语义检索

B. ontology + existing ranking
   本体查询 / 关系证据 + 现有确定性排序

C. ontology + Jev
   本体查询 / 关系证据 + Jev 选择或评分 + 现有治理闸门
```

Jev 失败时，C 必须降级到 B；本体没有覆盖时，B 和 C 可以回退到 A。任何路径都不能绕过权限、作用域、敏感度、版本和资产生命周期检查。

## 2. 测试数据边界

测试数据应来自用户实际沉淀的数据，或者来自明确标注的脱敏夹具。不能把 `985/211`、员工、API 网关等会议例子写进产品默认数据。

每条样本至少包含：

```json
{
  "id": "case-001",
  "task": "用户任务原文",
  "ontology": {
    "entities": [],
    "relations": [],
    "paths": []
  },
  "candidateAssets": [],
  "expected": {
    "assetIds": [],
    "allowNone": true,
    "evidenceRelations": []
  },
  "sensitivity": "synthetic-or-redacted"
}
```

标注结果由人工确认，至少包含：正确候选、明确不应选择的候选、允许返回 `none` 的条件和应展示的证据路径。

## 3. 功能验证

### 3.1 本体查询正确性

验证：

- 实体名称和别名能对齐到用户本体中的实体；
- 关系方向正确；
- 反向关系查询正确；
- 1-2 跳导航不重复、不循环；
- 关系不存在时明确返回无覆盖，而不是编造结果；
- 返回实体、关系、来源和路径证据。

验收建议：

- 关系查询 precision >= 0.90；
- 关系查询 recall >= 0.85；
- 证据路径完整率 >= 0.95；
- 不存在关系时编造率 = 0。

### 3.2 候选资产复用正确性

验证：

- 本体关系能够召回正确能力资产；
- 资产必须先通过本地硬性准入；
- `conflicts_with`、禁止条件和作用域限制生效；
- 已暂停、过期、版本不一致或无权限资产不能进入 Jev 输入；
- 候选为空时可以安全回退。

### 3.3 Jev 结构化判断

验证三类问题：

- `Choice`：选择候选资产或 `none`；
- `Score`：对适用性、相关性和结果质量评分；
- `Noul`：判断适用条件、证据充分性和冲突陈述。

验收：

- 返回结果通过本地 schema 校验；
- 未知 question ID、非法选项和越界分数被拒绝；
- 低置信度不自动注入高风险资产；
- `none` 不被改写成任意候选；
- Jev 结果不能直接修改本体或正式资产。

## 4. 降级和故障验证

必须覆盖：

| 故障 | 预期行为 |
| --- | --- |
| 没有 Jev API Key | 不调用 Jev，走 B 或 A |
| Jev 超时 | 记录降级，走现有排序 |
| Jev 限流 | 有界重试，随后降级 |
| Jev 返回非法结构 | 拒绝结果并降级 |
| Jev 网络错误 | 不影响主对话 |
| 本体图谱损坏或不可读 | 不编造关系，按策略回退 |
| 本体无相关实体 | 明确无覆盖，允许语义检索 |
| 候选全部被权限过滤 | 返回无可用资产，不发送给 Jev |
| 本体和资产版本变化 | 重新计算或拒绝旧结果 |

关键验收：CogSeed 的基础对话和普通检索不依赖 Jev 可用性。

## 5. 安全和隐私验证

检查：

- API Key 不出现在日志、回执和仓库；
- 未授权资产正文不进入 Jev 请求；
- 请求只发送完成判断所需的最小 state；
- 用户关闭 Jev 后不再发起请求；
- Jev 返回文本按不可信数据处理，不作为系统指令执行；
- Jev 不可直接写资产、本体、关系或权限配置；
- 跨作用域和高敏感资产需要本地确认流程；
- 回执记录摘要和引用，不默认记录完整敏感正文。

## 6. 质量和效果指标

对每条任务记录：

```json
{
  "caseId": "case-001",
  "route": "ontology_jev",
  "selectedAssetIds": [],
  "expectedAssetIds": [],
  "precision": 0,
  "recall": 0,
  "mrr": 0,
  "noneCorrect": false,
  "hardGateViolations": 0,
  "latencyMs": 0,
  "jevLatencyMs": 0,
  "fallback": false,
  "resultQuality": 0,
  "evidenceComplete": false
}
```

核心指标：

- 候选 precision / recall / F1；
- 正确 `none` 比例；
- 资产复用成功率；
- 错误注入率；
- 权限或作用域绕过次数，必须为 0；
- 证据路径完整率；
- Jev 调用成功率和降级率；
- P50/P95 延迟；
- 单任务调用成本；
- 用户纠正率和撤销率。

## 7. 对照验收门槛

建议先使用离线评估集，不直接改变默认线上行为。候选默认开启需要同时满足：

1. C 的候选 F1 不低于 B，且明显优于 A；
2. 错误注入率不高于 B；
3. 硬性治理绕过次数为 0；
4. `none` 判断准确率达到人工可接受门槛；
5. Jev 降级后 B 的行为保持稳定；
6. P95 延迟和成本在产品预算内；
7. 不同数据规模、空本体和脏关系数据下没有严重退化。

## 8. 分阶段验收

### Phase 1：适配器验收

只验证 Jev 客户端和 `Noop/Fallback`：请求构造、响应校验、超时、重试、脱敏和降级。

### Phase 2：候选选择验收

验证本体证据经过硬闸后进入 Jev，Jev 选择或拒绝候选，失败回退到现有排序。

### Phase 3：执行前验收

验证作用域、版本、冲突和敏感度策略不被 Jev 结果绕过。

### Phase 4：结果验证验收

验证 Jev 对执行结果产生质量信号，但不会绕过现有资产候选、审核和晋升流程。

### Phase 5：真实数据对照验收

在获得脱敏真实任务集后，比较 A、B、C 三条路径，并形成是否默认开启的结论。

## 9. 明确不能作为验收的内容

- 只拿固定的 API 网关示例证明通用能力已经完成；
- 只看到 Jev 返回 JSON 就认为资产复用正确；
- 只验证本体图谱能保存数据，就认为自然语言查询已经完成；
- 只验证向量召回数量，不验证关系方向和证据；
- 把 Jev 的判断当作事实来源；
- 把方案文档、测试脚本或演示夹具当成生产闭环。

## 10. 当前基线结论

最新 develop 已有本体图谱、R-Box、任务契约、混合资产检索和资产投影准入测试。本方案新增的 Jev 适配器、Jev 候选判断、结果验证和三路对照评估尚未实现。

当前只能验收为：

> CogSeed 已具备参考 Semantica 思路的本体驱动能力复用基础；Jev 接入需要按 Phase 1-5 继续实现和验证。
