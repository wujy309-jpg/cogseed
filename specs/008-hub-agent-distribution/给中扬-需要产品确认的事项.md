## 1. 依赖版本规则（你第 3 条要求补齐的）

**我目前的做法：**

| 情形 | 做法 |
|---|---|
| 本机已有该 Skill 且可用 | **直接复用，不升级。**不因为装一个 Agent 去改动别的 Agent 正在用的 Skill |
| 本机没有（缺的补装） | 安装 Hub 上**当前最高已发布版本** |
| 最高版本要求更高的客户端 | **阻断，提示"需 CogSeed x.y+"。**Hub 目录只返回最高版本，**没法回退到较旧的兼容版本**，Hub 已确认本期不支持回退 |
| 依赖受阻（本机的依赖被 Hub 停用，或最高版本要求更高客户端） | 安装前就阻断并说明原因；已装的 Agent 卡片显示"依赖已停用"，"使用"按钮不可点。**只影响这一个 Agent，不影响其他可用 Agent 与在途任务** |
| 本机缺少某个依赖（已装 Agent） | 只在卡片上提示"缺少依赖"，**不禁用"使用"**（存量 Agent 里有早就失效的旧引用，运行时本来就忽略，禁用会误伤） |
| 装完之后依赖有新版本 | 走 Skill 自己的更新通道，Agent 不触发升级；在途任务继续用已固定的版本 |
| 依赖后来被停用 | 不自动停用 Agent；只是这个 Agent 暂时不可用。注：Hub 要求先停用依赖它的 Agent 才能停用 Skill（否则返回 `409 CONTENT_IN_USE`），所以"本机装了、Hub 却停了"只会出现在这个先后窗口之后 |
| 安装或更新中任何一步失败 | 整个 Agent 不记录，原有 Agent、已装 Skill、在途任务都不受影响 |

**需要你确认：**
- 上面这套是否就是你要的规则？
- 特别是"最高版本不兼容就阻断、没有回退"：这会让个别用户在客户端较旧时装不上某个 Agent。接受吗？（要回退的话需要 Hub 另外返回多个版本，是 Hub 的新增工作。）

## 2. Agent 自己有新版本时怎么办（更新流程，目前没做）

我没有做更新界面，是因为要先定下面这些行为：

| 问题 | 我的建议 |
|---|---|
| Agent 有新版本时是否自动更新 | 与 Skill 一致：Hub 发布后客户端自动跟随，在途任务不受影响 |
| 新版本的随包私有 Skill | 整体替换，不与旧版混用 |
| 新版本依赖的 Hub Skill | 按第 1 条规则：已有的复用，缺的补装 |
| 更新失败 | **保留旧版并继续可用**，在卡片和详情页提示"更新失败，仍可使用 1.x" |
| 更新后用户的启停选择 | **保留**：原来停用的更新后仍停用，不替用户启用（建议） |
| 已被用户停用的 Agent 能否更新 | **能更新，更新后仍保持停用**（建议） |
| 随包私有 Skill 本地改过 | **整体替换，本地修改会丢**——这是明确的代价，需要你认可 |
| 用户想停在旧版 | 本期不做（"转为我的版本"之类留到后续） |
| 新版本是否有"更新了什么"提示 | 卡片显示本机版本；更新失败时提示"仍可使用 x.y" |

**需要你确认：**上面这套（特别是新增的三行：启停保留、停用的也更新、本地修改被替换）是否可以？**更新失败保留旧版、卡片提示已经做完**；"是否有新版本"的判断也已按 Hub 目录规则写好，接真实接口等联调。

## 3. 贡献时要不要自动处理正文里的本机路径和疑似凭据

**现状：**客户端只做两件事，都在本机，**Hub 不知道处理了什么**：
1. 移除不该分发的字段：版本和时间戳、连接器配置、模型偏好等；
2. 拦住最明显的密钥格式（SSH 私钥、pem 等），拦住后不允许提交。

**已做（按 Hub 规格 US3 场景 3a）：**预览页会把正文和随包文件里**明显**的本机路径（例如 `/Users/xxx/发票/`）、疑似凭据高亮出来，用户勾选"已知晓"才能提交；**只高亮、不自动改写**，Hub 也不知道命中了什么。

**不会做的：**不自动替换作者原文，不穷举。预览页会把全部要发出的内容给用户看，由用户自己确认。

**我的建议：保持现状（高亮提示 + 用户确认，不自动改）。**理由：自动替换会悄悄改作者的原文，容易改错；评审会的结论也是"只拦最明显的，不穷举，不做成长期规则库"。

**需要你确认：**是否同意这个做法？
