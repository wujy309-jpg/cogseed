## 〇、结论先行

「待我处理」功能上是通的，但长出了**三条并存的确认链、三套候选/资产模型**，且有两条用户旅程真断点（点了必报错的治理按钮、静默注入线里永远被拦的跨作用域资产）。**页面分区骨架是 09-26/09-28 刚定的稿，不动**；重构主轴三件事，全部发生在分区内部与后端链路：

1. **一物一链一位置**——一条候选只有一条确认链（候选详情的完整三选一流程）、只出现在「要你拍板」一个分区；治理行不再自成一套确认。
2. **断的接上、死的拆掉**——`resume` 恢复入口、治理分区事件刷新、读失败错误态、四语硬编码；旧认知页死路由、三套模型、断头生产线拆退役。
3. **读写面收敛**——列表服务端过滤、动作响应当场消费、砍零消费字段、通道面退役。

规模：5 个批次（第 1 批纯 bug 修复先行，第 5 批退役依赖拍板）。两个前置收口（并行线工作区提交、分支远端备份）+ 8 个拍板点，见文末。

## 三、目标设计

### 3.1 先过 User Story（09-20 铁律：治理概念不上界面）

「待我处理」页只回答四句话：

- **US-R1**「AI 想让我记一件事」→ 一列候选，每条一句话 + 点开看依据与全文。
- **US-R2**「我现在没空」→ 稍后处理；以后在「已稍后处理」里找得到、**恢复得了**。
- **US-R3**「这条不对」→ 拒绝或改了再存；处理记录如实（已保存/未保存/已忽略）。
- **US-R4**「来源没了/证据不足」→ 如实降级显示（子标记章），**绝不把读失败伪装成『没有待办』**。
- 治理概念（冲突消解、边界规则、跨作用域授权、投影状态）全部内部化——系统自己消化，只在必须有用户决定时以一句人话浮出。

### 3.2 目标形态

**🔴分区骨架不动**（09-29 复审修正）：页面现有分区结构——「要你拍板（治理 confirm+候选合流）→ 证据异常 → 低打扰 → 已稍后处理 → 已失效/处理记录 → 其他异常」+ 三口径计数（要你拍板/低打扰/证据异常）+ 导语锚点跳转——是 2026-09-26 specs/018 v2 真机重做、09-28 两页重整刚定的稿，**本方案不重排分区**（原稿「六组→四区」基于对现状结构的误读，已撤回）。重构聚焦分区**内部**的链路、数据流与反馈：

1. **一物一链**：候选确认只有一条链 = 候选详情确认界面（promote 完整三选一：相似资产/版本冲突/高风险）。治理行（`cognition.inbox`）撤出候选确认类条目（candidate_pending_review 停产），accept/claim 直调 promote 的两处分支删除；`proposal:` 链（保存更新）第 2 批一并审闸门一致性。治理行只收系统自查类（冲突与重复、巡检发现），每行只渲染有真实出口的动作。
2. **一物一位**：同一条 pending 候选只出现在「要你拍板」分区一处（现状候选卡+治理行双入口去重）。徽章计数（含树根「待你处理 N 条」）同步单一口径。
3. **反馈闭环**：动作就地消费响应体 `{ok, candidate}` 更新 store（core.js:1883 现状丢弃返回值），失败进显式错误态；「已稍后处理」每条带「恢复」按钮（resume 接通）；reload 不吞（loading 窗口记 pending 补拉）；治理分区获得 `cognition:changed` 事件刷新。
4. **读失败不伪装**：`recall.candidates.list` 失败显示错误态+重试按钮，不再 soft 降级成「现在没有要你决定的」空态。
5. **读模型收敛**：`recall.candidates.list` 服务端 bucket 过滤（复用 asCandidate 同一口径）+ 视图字段瘦身（去 16 候选字段+8 capabilities 标志的零消费传输）。
6. **后端收敛**：三套模型 → 一套（recall 候选正本 + asCandidate 读模型）；旧 `cognition.*` 死通道族退役。
