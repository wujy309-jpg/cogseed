## 2. 先认识这个产品：cogseed 与核心术语

**应用形态**：cogseed 是桌面端 AI 协作应用。用户在群聊式界面发起任务，多个 AI 参与者协作完成；应用分主进程（后台部分，管数据存储与业务逻辑）和渲染层（用户看到并点击的界面），两者靠 IPC（进程间通信，一条互相调用的通道）说话。「真机」指真实运行的应用环境，相对自动化测试环境而言。

**角色与系统**：

| 名字 | 是什么 |
|---|---|
| 群聊任务 | 在群聊界面发起、交给 AI 执行的任务；「终态」指任务走到最终状态（完成/失败等结束点） |
| Commander | 主控智能体：接任务、编排派发、拼装每轮对话背景（召回注入发生在它这一层） |
| Agent / Worker | 被 Commander 派发干活的执行智能体。它们不享受自动召回、只拿 Commander 显式授权的资产清单——这是权限设计：被派发者不自行取用用户记忆 |
| KStar | 复盘与归因系统（材料中亦写作 KSTAR，是同一系统的两种拼法，本文统一作 KStar）：任务收口后对账「哪些资产真的被用了」，产出经验与改进候选 |
| memory 模块 | 应用里更早的通用记忆模块，存 MEMORY 记录（旧的用户记忆条目）；旧体系资产确认后经事务桥接写入它，它侧删除会反向作废资产 |
| 世界模型 | 支撑层组件，存因果规则与预测、用于对账（材料着墨少，细节未展开） |

**核心概念**：

| 名字 | 是什么 |
|---|---|
| 资产（AbilityAsset） | 通过审查的正式知识条目，带版本、审计、敏感度分级。分类口径两说并列：代码勘察记五类 personal/fact/rule/template/skill_method；文档勘察记 PRD v0.4 定四类（关于我/规则与偏好/模板与范例/技能与方法）且与代码 personal/rule/template/skill_method 一一对应。fact 何时引入、PRD 是否同步更新，材料未说明，需对照 |
| 候选池 / 晋升 | 候选池是草稿区，LLM 提炼出的条目先放这里等用户审查；晋升是确认后转为正式资产 |
| 本体 | 用户个人知识的分类体系：个人本体（关于「我」的事实/规则）+事项本体（关于具体事情）+分类体系+关系网络，图谱存 ontology-graph.json。界面上的「本体组」是它的分组编辑视图；「三盒」指本体组按个人事实/规则/模板三类内容分成的三个编辑盒 |
| 认知树 | 面板第一页签，把资产按树形总览展示 |
| 投影 | 决定哪些资产进入某轮对话背景的快照记录；授权来源分用户确认/工作区策略/宿主自动/模型自选四类 |
| 注入 | 把选中资产拼进给模型的提示词（systemPrompt）；「带入」泛指资产进入对话上下文的动作（读取/派发/引用都算带入，但按拍板口径都不算「采用」） |
| 回执 / applied | 每次注入与使用的留痕记录；applied（实际采用回执）是「资产真被用上」的唯一权威判据 |
| 红队测试 | 安全视角自查：模拟攻击者找漏洞 |
| 存量 / 主链取证 / 回填 | 存量＝已有的旧数据；主链取证＝在真实使用主链路上取证据；回填＝执行后把结果写回记录 |
| specs 编号 | 007-019 等编号指工程规格目录（Spec Kit 制品）下的工作线编号，一个编号一条工作线；正本不进 git，文档库存有 09-24 备份。第 5 章阶段表与第 7 章的 009/012/013/014、015/016、007、019、020 均出此系 |

## 4. 它是怎么运转的

### 4.1 主进程：写入 → 存储 → 召回的链路

**第一步，写入（三条入口，汇进同一个候选池）。**

1. 自动捕获：群聊任务到终态后，若用户在沉淀设置里显式开启夜间模式（nightly），捕获编排器排队一条任务（`src/main/features/recall/capture-service.ts:3340`），到点挑消息、调 LLM 按提炼提示词输出最多 3 条候选；没配置模型时用本地命令行 AI 工具兜底（材料举例 claude）。任务一结束就自动整理的 smart 策略保持下线，理由写在 `src/main/features/recall/capture-service.ts:3326` 注释（判断不成熟，以手动为主）。
2. 手动沉淀：用户在界面对某条消息点「沉淀」（IPC `cognition.capture.draft`，`src/main/ipc/cognition.ts:36`），围绕该消息取最多 24 条上下文让 LLM 出草稿，确认后走 `recall.candidates.save` 进候选池。
3. 显式教学：用户消息里出现明确「记住/保存/更正」指令时（多语言正则，故意保守），产生候选或教学信号，同入候选池。

**第二步，审查晋升。** 候选先过准入门（正则层 + 语义层防投毒），用户在待办收件箱做决定（保存/改后保存/暂缓/拒绝，每个决定落审计账本），晋升时 create 新建或 update 基于在用版融合生成新版本，建立带版本、审计、敏感度分级的资产（分类口径的冲突见第 2 章术语表）。

**第三步，存储。** 经 store 落盘（格式见第 3 章注解），每次写入通过 `cognition:changed` 通道向界面广播（50ms 合并窗口），广播层 `src/main/features/recall/store-events.ts` 于 09-27 刚重写。

**第四步，召回注入。** 新任务回合派发时（`src/main/features/group_chat/bus.ts:5809`），优先使用需求生命周期里已确认的 committed 投影，否则现场按任务文本自动检索选资产；每条资产再过运行时准入门（暂停/不成熟/越域/敏感度不符的剔除并记省略原因），合成不超过 14k 的提示词块拼进 systemPrompt。被派发的 Agent/Worker 回合不享受自动召回，只注入 Commander 显式授权的资产清单（`src/main/features/group_chat/bus.ts:5941`）。

**第五步，回执闭环。** 注入同时落回执（按回合去重）与使用流水；任务收口时 KStar 归因模块（`src/main/features/kstar/secondary-attribution.ts`）对账流水与回执，判断资产是否真被用，效果反馈回写排名权重。

**第六步，目录快照。** 每回合给提示词常驻一份紧凑目录文本（每条不超过 110 字符）加使用统计，模型可自取，省一次工具往返——这是目录算法 v2 的产物。

以上 3 条候选、24 条上下文、14k、110 字符等上限值均出自代码/材料；是否可配置、定值依据，材料未说明。
